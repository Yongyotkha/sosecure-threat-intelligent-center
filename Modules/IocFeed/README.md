# คัมภีร์การใช้งานระบบ IoC Feed Near Real-Time (ฉบับละเอียดที่สุด) 🛡️✨

คู่มือฉบับนี้จัดทำขึ้นเพื่อให้ผู้ดูแลระบบ (Admin) และฝ่ายเทคนิค (Network/Security) เข้าใจการทำงานทั้งหมดของระบบ IoC Feed อย่างลึกซึ้ง

---

## 1. 🏗️ สถาปัตยกรรมและการไหลของข้อมูล (Data Flow)

ระบบนี้เปลี่ยนจากการรัน Batch แบบดั้งเดิม (ที่ต้องรอนาน) มาเป็นระบบ **Near Real-Time** โดยมีขั้นตอนดังนี้:

1. **Enrich / New Event:** เมื่อมีการแก้ไขคะแนนหน้าเว็บ หรือมี Event ใหม่เข้ามา
2. **Sync Engine (1 min):** คำสั่ง `ioc-feed:update` จะตรวจพบการเปลี่ยนแปลงภายใน 60 วินาที
3. **Feed Storage:** ข้อมูลจะถูกจัดระเบียบและเก็บไว้ในคอลเลกชัน `fx_ioc_feeds`
4. **API Delivery:** เมื่อระบบภายนอกเรียก API ระบบจะดึงข้อมูลที่เตรียมไว้แล้วส่งออกแบบทันที (High Performance)

---

## 2. 📅 เจาะลึกตรรกะของวันที่ (Date Logic Deep Dive)

ในไฟล์ CSV จะมีวันที่ 2 ชุดเสมอ เพื่อตอบโจทย์ความแม่นยำและการนำไปใช้งานจริง:

### ก. ioc_timestamp (วันที่ประวัติศาสตร์ - Column 3)
> ตัวอย่าง: `22/01/2026 23:42`
- **คืออะไร?**: วันที่ดั้งเดิมที่ไอพีตัวนั้นปรากฏตัวครั้งแรกใน Event หรือ Pulse นั้นๆ
- **หน้าที่**: ใช้สำหรับตรวจสอบความเกี่ยวข้องทางประวัติศาสตร์ (Forensics) ว่าเหตุการณ์จริงเกิดเมื่อไหร่

### ข. sending_timestamp (วันที่อัปเดตล่าสุด - Column 4)
> ตัวอย่าง: `01/04/2026 15:21`
- **คืออะไร?**: วันที่ล่าสุดที่มีกิจกรรมเกิดขึ้น (เช่น วันที่คุณเพิ่งกด Enrich แก้ไขคะแนน)
- **หน้าที่**: **สำคัญที่สุดสำหรับการบล็อก!** เพราะ Firewall ส่วนใหญ่จะเชื่อถือข้อมูลที่ "สดใหม่" (Fresh) การที่เราส่งเวลาวันนี้ไปให้ Firewall แม้เหตุการณ์จะเกิดในเดือนมกราคม จะช่วยให้ Firewall มั่นใจและทำการบล็อกให้ทันที

## 3. 🌍 การใช้งาน API Export (API Reference)

คุณสามารถดึงข้อมูลผ่าน URL: `GET /api/v1/ioc-feed/{category}.csv`
*(หมวดหมู่: `ip_address`, `domain`, `hashfile`)*

### ตัวกรอง (Query Parameters):

| Parameter | ค่าที่ใส่ได้ | คำอธิบายเจาะลึก |
| :--- | :--- | :--- |
| **`token`** | `YOUR_TOKEN` | **จำเป็น!** ระบุ Token ความปลอดภัยตามที่ตั้งไว้ใน `.env` (`IOC_FEED_TOKEN`) |
| **`is_public`** | `1`, `0`, `all` | `1` เอาเฉพาะ Public Event, `0` สำหรับ Private Event (ถ้าไม่ใส่เลยระบบจะเอา **ทั้งหมด** เพื่อไม่ให้ของเก่าหาย) |
| **`timeframe`** | `1h`, `6h`, `1d`, `1w` | กรองเอาเฉพาะข้อมูลที่มีกิจกรรม (เพิ่งอัปเดต) ในช่วงที่กำหนด |
| **`with_whitelist`** | `1`, `0` | ปกติระบบจะ **กรอง Whitelist ทิ้งเสมอ** ถ้าอยากได้ไอพีที่ปลอดภัยด้วยให้ใส่เป็น `1` |

#### 💡 ตัวอย่าง URL:
- **ดึงเฉพาะ Public ที่อัปเดตย้อนหลัง 1 วัน:** 
  `https://your-domain.com/api/v1/ioc-feed/ip_address.csv?is_public=1&timeframe=1d`

## 5. ⚪️ ระบบการจัดการ Whitelist (แบบละเอียดเจาะลึก)

ระบบมีกลไกป้องกัน **False Positive** โดยการอนุญาตให้ระบุ "ไอพีปลอดภัย" เพื่อไม่ให้ไปขัดขวางการทำงานปกติของระบบเครือข่าย

### ⚙️ กลไกการทำงานของ Whitelist:
1. **การตรวจสอบ (Synchronization Phase):** ทุกครั้งที่รัน `ioc-feed:update` ระบบจะโหลดรายชื่อไอพีจากตาราง `fx_ioc_whitelists` มาเก็บไว้ในหน่วยความจำ
2. **การทำเครื่องหมาย (Flagging):** หากพบว่าไอพีใน Feed ตรงกับ Whitelist ระบบจะทำการปั๊มตรา **`is_whitelisted: true`** ลงไปในข้อมูลตัวนั้นทันที (แต่ข้อมูลจะไม่ถูกลบทิ้ง เพื่อเก็บไว้ดูย้อนหลัง)
3. **การกรองออก (API Phase):** โดยปกติแล้ว API จะ **"ซ่อน"** ข้อมูลที่มีสถานะ Whitelist ไว้เสมอ เพื่อให้ไฟล์ CSV ที่ส่งไปยัง Firewall สะอาดและปลอดภัยที่สุด

### 🌍 วิธีควบคุมผ่าน API:
- **โหมดปกติ (ไม่เอา Whitelist):** เรียกใช้งาน URL ปกติ (ระบบจะกรองออกให้อัตโนมัติ)
- **โหมดรวมทั้งหมด (รวม Whitelist):** เติมพารามิเตอร์ `&with_whitelist=1` ต่อท้าย URL
  > *ตัวอย่าง: `/api/v1/ioc-feed/ip_address.csv?with_whitelist=1`*

## 6. 📊 รูปแบบข้อมูลในไฟล์ (CSV Format)

> **รูปแบบ:** `[INDICATOR],[SCORE]|[START_TIME]|[END_TIME]|[CATEGORY]|[SEVERITY]|[INDICATOR_ID]|[EVENT_ID]|[EVENT_NAME]`

### ความหมายรายคอลัมน์:
1. **INDICATOR:** ตัวไอพี หรือ โดเมน
2. **SCORE:** คะแนนอันตราย (0-10)
3. **START_TIME:** วันที่เกิดเหตุจริง (History)
4. **END_TIME:** วันที่อัปเดตล่าสุด (Freshness)
5. **CATEGORY:** ประเภทข้อมูล (เช่น IPv4, Domain)
6. **SEVERITY:** ระดับความรุนแรง (Critical, High, Medium, Low)
7. **INDICATOR_ID:** รหัสอ้างอิงของ Indicator
8. **EVENT_ID:** รหัสของหน้าคดี (Pulse ID)
9. **EVENT_NAME:** ชื่อหน้าคดี (อาทิ ElasticPot, HoneyNet)

## 7. 💡 ตัวอย่างสถานการณ์การใช้งานจริง (Common Use Cases)

เพื่อให้เห็นภาพการนำไปใช้ ผมสรุปตัวอย่างที่พบบ่อยไว้ดังนี้ครับ:

### ก. การดึงข้อมูลไป Block ที่ Firewall (เน้นความสดใหม่)
**โจทย์:** ต้องการ IP ที่เป็นสาธารณะ (Public) และเพิ่งอัปเดตใน 1 ชั่วโมงล่าสุดเท่านั้น
**URL:** `/api/v1/ioc-feed/ip_address.csv?is_public=1&timeframe=1h`

### ข. การตรวจสอบข้อมูลดิบทั้งหมด (For Admin/Audit)
**โจทย์:** ต้องการดู IP ทั้งหมดที่มีในระบบ (รวม Private และ Whitelist) เพื่อตรวจสอบย้อนหลัง
**URL:** `/api/v1/ioc-feed/ip_address.csv?is_public=all&with_whitelist=1`

### ค. เมื่อมีการแก้ไขคะแนนตัวกลุ่มใหญ่ (Manual Sync)
**โจทย์:** คุณเพิ่งกด "Enrich" ไอพีจำนวนมาก และอยากให้มันเข้าระบบทันทีโดยไม่ต้องรอคิว
**คำสั่ง:** `php artisan ioc-feed:update --lookback=3600` (ซิงค์ย้อนหลัง 1 ชม. ทันที)

## 📊 8. ตัวอย่างข้อมูลในไฟล์ (Data Sample)

หน้าตาของข้อมูล 1 บรรทัดใน CSV จะเป็นแบบนี้ครับ:
`205.210.31.230,9|22/01/2026 23:42|01/04/2026 15:21|IPv4|Critical|3664414749|69721b80984a56a25ae421fd|HoneyNet Data`

**คำอธิบายตัวอย่าง:**
- `205.210.31.230`: ไอพีพ่วงมาด้วยคะแนนความเสี่ยง `9`
- `22/01/2026 23:42`: วันที่เกิดเหตุครั้งแรก (History)
- `01/04/2026 15:21`: วันที่อัปเดตล่าสุด (Freshness) **<- ตัวนี้ที่ Firewall จะใช้เช็ก**
- `IPv4 | Critical`: ประเภทและความรุนแรง
- `3664414749 | 69721b...`: ID ของไอพีและคดีอ้างอิง
- `HoneyNet Data`: ชื่อ Event ที่มาของข้อมูล

## 🛠️ 9. วิธีการแก้ไขปัญหาเบื้องต้น (Troubleshooting)

- **ทำไมข้อมูลไม่ขึ้นใน CSV?**: เช็กว่ารัน `php artisan ioc-feed:update` หรือยัง? และไอพีนั้นติด Whitelist หรือไม่?
- **ทำไมวันที่ส่งเท่ากันหมด?**: เป็นเรื่องปกติครับ เพราะมันคือวันที่ระบบ "ยืนยันความสดใหม่" ของข้อมูลชุดนั้น เพื่อให้ Firewall ยอมบล็อกให้ครับ (ดูรายละเอียดในหัวข้อที่ 2)
